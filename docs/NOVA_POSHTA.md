# Довідник відділень Нової пошти

Чекаут підказує місто і відділення з локальної копії довідника. Поки копії немає, покупець як і раніше вводить місто й адресу вручну.

## Ключ API

Довідник `getWarehouses` відповідає навіть з порожнім ключем. Ключ Бізнес-кабінету знадобиться пізніше для створення ТТН, не для цього пошуку.

У `.env` на сервері (файл не комітити):

```
NOVA_POSHTA_API_KEY=
```

Порожнє значення лишайте, доки ключ не потрібен. Після зміни `.env` перестворіть контейнер, інакше процес не побачить нову змінну:

```
docker compose up -d backend
```

## Повний синк

На проді:

```
docker compose exec backend python manage.py sync_np_warehouses
```

Команда сторінками забирає відділення, оновлює наявні записи і лише після повного успішного проходу вимикає ті, яких більше немає у відповіді. Якщо сторінка або мережа падає, уже завантажені рядки лишаються, а зниклі відділення не вимикаються.

Синк можна запускати без ключа.

В адмінці довідника Нової пошти немає: ні списку відділень, ні кнопки синку. Оновлення — лише командою вище (прохід триває кілька хвилин).

## Де дивитися статус

**1. Вивід команди.** Після завершення `sync_np_warehouses` друкує підсумок, наприклад:

```
Синхронізацію завершено: сторінок 111, отримано 55426, створено 0, оновлено 55426, деактивовано 12.
```

Якщо синк не вдався, команда друкує причину (без ключа) і завершується з кодом 1. Якщо інший синк уже виконується (молодший за 2 години), новий не стартує і команда про це повідомляє.

Щоб зберегти вивід у файл на сервері:

```
docker compose exec -T backend python manage.py sync_np_warehouses > np_sync_$(date +%Y%m%d).log 2>&1
```

**2. Журнал синків у базі (`NPSyncRun`).** Останні запуски і кількість активних відділень:

```
docker compose exec -T backend python manage.py shell -c "
from novaposhta.models import NPSyncRun, NPWarehouse
for r in NPSyncRun.objects.order_by('-started_at')[:5]:
    print(r.started_at, r.status, r.pages, r.received, r.deactivated, r.message)
print('Активних відділень:', NPWarehouse.objects.filter(is_active=True).count())
"
```

Статуси: `running` — виконується, `success` — успішно, `failed` — помилка (текст у `message`, без ключа). Запис `running`, старший за 2 години, наступний запуск сам позначить як `failed`.

**3. Перевірка пошуку на сайті.** `GET /ua/api/np/cities/?q=ки` має повертати `"available": true` і список міст. `"available": false` означає, що довідник порожній або недоступний — чекаут тоді приймає місто й відділення ручним текстом.

## Розклад

Має сенс оновлювати довідник щодоби, наприклад cron на сервері:

```
0 4 * * * cd /шлях/до/проєкту && docker compose exec -T backend python manage.py sync_np_warehouses
```

Окремий сервіс у `docker-compose` під цей синк **не вмикайте**, доки розклад не узгоджений. Команда безпечна для повторного запуску, але два повні проходи одночасно не стартують: якщо вже є синк молодший за 2 години, новий пропускається.

## Індекс пошуку

Міграція на PostgreSQL виконує `CREATE EXTENSION IF NOT EXISTS pg_trgm` і GIN-індекси по нормалізованому тексту відділень і міст. З PostgreSQL 13 `pg_trgm` є trusted: розширення може створити роль із правом `CREATE` на базу, суперкористувач не обовʼязковий. Якщо права немає, міграція зупиниться на цьому кроці — індекс треба створити вручну під роллю, якій це дозволено. На SQLite цей крок нічого не робить, пошук лишається звичайним `LIKE`.
